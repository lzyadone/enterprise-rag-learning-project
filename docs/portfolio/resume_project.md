# 简历项目包装与面试表达

这份材料用于把“企业级智能知识库与问答平台”转换成招聘方容易阅读、面试时也能解释清楚的项目经历。推荐目标岗位是 AI 应用开发、RAG/LLM 应用工程师或 Python 后端开发。

项目仓库：[enterprise-rag-learning-project](https://github.com/lzyadone/enterprise-rag-learning-project)

## 1. 使用原则

1. 简历只放最有区分度的 4-5 条，详细内容留给项目链接和面试。
2. 使用“动作 + 技术 + 结果”的句式，不只罗列工具名。
3. 只保留自己能解释清楚的内容；不熟悉的模块先按本文后半部分准备。
4. 这是个人学习与作品集项目，应写成“个人项目”，不要虚构公司、客户、线上用户量或商业收益。
5. `Recall@10 1.000` 只代表冻结的 32 题独立测试集，`12.67x` 只代表热缓存下的局部检索微基准，不能写成开放场景准确率或整站加速。

## 5. 60 秒面试自我介绍

我做了一个企业级 RAG 知识库个人项目。它不只是把文档放进向量数据库再调用大模型，而是把数据处理、检索、生成、评测、安全和索引发布串成了一套完整流程。

在检索层，我用 bge-m3 和 Chroma 做语义召回，用 BM25 补充关键词召回，再通过 RRF 融合。我还为复杂问题设计了受约束的拆解机制，因为早期方案会产生过多检索任务，既增加延迟，也可能偏离用户原意。优化后，开发集平均检索任务从 18.22 次降到 1.81 次，并通过独立测试集的无退化门槛；由于没有证明质量显著提升，我将它保留为可选能力，没有贸然替换稳定的默认路径。

在工程层，我实现了不可变版本索引、增量复用、候选验证、原子切换和回滚，还把提示注入、凭据请求和知识边界处理放在检索与模型调用之前。最终项目使用统一质量入口运行 139 项测试、8 项安全案例和前端检查，并接入 GitHub Actions。我通过这个项目掌握的不只是 RAG 组件调用，更重要的是如何用评测和发布门槛控制一个 AI 功能的风险。

## 6. 三个重点面试案例

### 案例一：为什么复杂问题拆解没有直接替换默认策略

**背景：** 早期的复杂问题拆解方案平均产生 18.22 个检索任务，速度慢，而且过度扩展可能改变用户原意。

**任务：** 在保留复杂问题覆盖能力的同时，减少不必要检索，并判断新策略能否安全发布。

**行动：** 重新设计受约束的拆解规则：具体问题只使用原始问题，至少识别两个明确回答面时才扩展，扩展查询保留原问题，并限制知识类别、回答面和检索任务总数。先在开发集迭代，再冻结 32 题独立测试集、候选结果、相关性标签和发布门槛。

**结果：** 开发集平均检索任务从 18.22 次降到 1.81 次；独立测试中，优化策略与稳定基线都取得 Recall@10 1.000、nDCG@10 0.843，Top-10 结果完全重合。结论是优化没有造成退化，但也没有证明显著提升，因此只作为可选实验能力，默认策略保持不变。

**这个案例证明：** 能区分开发集与独立验证，也能根据证据做克制的发布决定。

### 案例二：如何修复 PyPDFLoader metadata 知识缺口

**背景：** 评测中发现两个 PDFLoader 页码 metadata 问题缺少直接官方证据。问题不是检索算法失效，而是知识库来源不完整。

**任务：** 补充证据，同时避免为了让指标变好而修改旧题目或标签。

**行动：** 增加固定到具体 Git 提交的 PyPDFParser 与 TextSplitter 官方源码，并只提取目标类和方法；通过安全刷新构建候选索引，把两道题设为索引发布 required cases。

**结果：** 知识库从 52 份文档、938 chunks 更新到 54 份文档、942 chunks，两类问题的直接证据进入前列；旧评测集、相关性标签和历史分数保持不变，新索引通过门禁后才启用。

**这个案例证明：** 能定位 badcase 的真实层级，并保持实验历史可追溯。

### 案例三：为什么索引需要版本化和回滚

**背景：** 直接在活动 Chroma 库中增删数据，失败时可能留下新旧向量混合、删除来源残留或部分更新状态。

**任务：** 让知识库更新能够验证、切换和恢复。

**行动：** 每次更新创建不可变版本，通过来源哈希计算差异，复用未变 chunks 和 embedding；构建完成后校验 manifest、哈希、ID、文本、metadata 和数量，再原子切换 active pointer，同时保存上一版本。

**结果：** 基线 942 个向量可以完整复用，候选启用与回滚在同一 Web 进程内生效；索引发布失败不会影响当前活动版本。

**这个案例证明：** 能把 AI 数据更新当作正式的软件发布流程处理。

## 7. 高频追问与回答要点

### 为什么同时使用向量检索和 BM25？

向量检索擅长找到语义相近但用词不同的内容，BM25 擅长匹配类名、参数名、缩写和报错文字等精确关键词。两者覆盖的失败类型不同，因此先各自召回，再用 RRF 根据排名融合，比只依赖某一路更稳健。

### RRF 是什么？

RRF 是 Reciprocal Rank Fusion。它不要求把向量分数和 BM25 分数强行放到同一个尺度，而是根据候选在各列表中的名次累加分数。排名越靠前，贡献越大，实现简单且对不同检索器的分数范围不敏感。

### 为什么选择 bge-m3？

项目资料包含中英文技术文档，需要多语言语义表示。bge-m3 可以本地运行，便于复现实验，也避免必须把知识库文本发送到远程 embedding 服务。简历中不要把这一选择描述成“所有场景最优”，它只是符合本项目约束的选择。

### 为什么 cross-encoder 没有默认启用？

固定候选实验中，它没有提高总体 nDCG，却把每题重排耗时增加到约 4.8 秒。因此保留成可选能力，但没有因为模型更复杂就默认上线。

### 这个项目和普通 RAG Demo 最大的区别是什么？

普通 Demo 常停在“上传文档并回答问题”。本项目额外建立了独立测试集、相关性标注、索引版本、发布门禁、安全前置处理、模型回退、自动测试和 GitHub Actions，重点是让结果可解释、改动可验证、失败可回退。

### 目前还不够生产化的地方是什么？

独立测试集只有 32 题，相关性标签主要来自隐藏系统信息后的 LLM 盲标并经过小规模抽查；安全规则是确定性工程底线，不是完整权限系统；缓存是单进程内存缓存；本地模型仍可能出现引用格式波动。生产化还需要真人标注、更大规模真实业务流量、用户权限、多实例缓存和可观测性。
