这份记录关注“为什么这样做”，而不是重复功能列表。每个决定都包含证据和仍然存在的代价。

## D1：来源必须可追踪和可复现

**问题**：网页内容会变化，同一源码文件还可能包含相邻但无关的实现；只更新一个来源时也可能意外生成残缺知识库。

**决定**：用 source manifest 保存类别、优先级、URL 和固定提交；源码来源可限制到具体类或方法。定向刷新只控制下载范围，正式聚合仍要求全部 P0 来源存在，并通过临时文件原子替换。

**证据**：PyPDFLoader metadata 缺口通过固定官方源码补齐，知识库从 52/938 更新到 54/942，相关固定问题检索排名恢复，同时没有覆盖旧 benchmark。

**代价**：新增来源需要维护 manifest 和固定版本；这是换取可追溯性的显式成本。

## D2：按文档结构切分，不采用单一固定窗口

**问题**：固定 token 窗口会切断标题、段落、代码和结构化对象，导致 chunk 缺少可解释边界。

**决定**：优先沿 Markdown 标题、段落和文档结构切分，再用软硬长度限制处理异常长内容。

**证据**：当前 942 个 chunks 的构建检查没有超长或异常短片段；端到端 chunking 问题能返回结构边界相关证据。

**代价**：不同来源需要解析适配，切分逻辑比固定窗口复杂。

## D3：用 RRF 融合 Dense 与 BM25

**问题**：向量检索擅长语义相似，BM25 擅长产品名、API 名和精确术语；单路召回会稳定漏掉另一类信号。

**决定**：Chroma + bge-m3 与 BM25 并行召回，用 Reciprocal Rank Fusion 按排名融合，避免直接比较不可校准的原始分数。

**证据**：固定 8 题实验中，direct dense 双指标通过率为 62.5%，direct hybrid 为 75%；平均 evidence-term recall 从 0.738 提升到 0.838。

**代价**：增加一次稀疏检索和融合步骤；仍需 query planning 或数据修复处理复杂覆盖问题。

## D4：Planner v3 保守扩展，默认保持 direct

**问题**：旧 planner 平均每题运行 18.22 个检索请求，过度扩展会稀释原问题并放大延迟。

**决定**：conservative v3 只扩展已定义且至少有两个明确方面的 RAG 问题，其他问题保留原查询。Web 允许手动选择 planned v3 或 auto，但默认仍是 direct。

**证据**：开发集平均 runs 降到 1.81；独立 32 题 holdout 中 direct 与 planned v3 的 Top-10 完全重合，Recall@10 1.000、nDCG@10 0.843，auto 与 oracle 一致率 96.9%。

**代价**：holdout 只支持“无退化”，没有证明 planned v3 显著优于 direct，因此不能据此切换默认值。

## D5：cross-encoder 只保留为可选能力

**问题**：更复杂的重排器理论上能改善排序，但会增加 GPU 依赖、模型加载和推理延迟。

**决定**：支持 `BAAI/bge-reranker-v2-m3`，但默认继续使用轻量 lexical 路径。

**证据**：固定候选实验中，不重排 nDCG@k 为 0.725，cross-encoder multilingual 为 0.700；两者双指标通过率都为 100%，但 cross-encoder 每题增加约 4.79 秒重排时间。

**代价**：部分单题可能从 cross-encoder 获益；需要更好的人工 qrels 和领域数据后再决定。

## D6：记忆与事实证据分离

**问题**：把历史对话直接当作知识来源会让用户偏好、旧回答和外部事实混在一起，难以审计。

**决定**：短期和长期记忆只用于指代、偏好、目标和项目状态；外部事实必须来自本轮检索资料。记忆回答模式单独审计。

**证据**：上下文明确标记 memory 与 retrieved evidence 的角色，Web 端到端烟测包含长期偏好问题并通过。

**代价**：用户曾经提供的事实不会自动获得与知识库相同的可信度，需要显式入库或再次检索。

## D7：远程模型是临时显式选择

**问题**：作品演示需要兼容远程 API，但不应把密钥写入配置、日志、记忆或响应，也不能暗中把请求发送给第二个云端模型。

**决定**：支持 OpenAI Chat Completions 兼容接口；地址、模型和密钥只保存在当前页面与单次请求。远程模式不自动回退 Ollama，也不触发 DeepSeek 修复或审计。

**证据**：桌面和手机视口、连接错误收敛、刷新清空和响应无凭据测试均已通过。

**代价**：刷新后需要重新填写；Azure 特有 header/query 协议不在当前范围。

## D8：索引必须版本化并通过门槛后启用

**问题**：直接重建活动 Chroma 会产生部分更新、旧向量残留和无法回滚的风险。

**决定**：每次构建不可变候选版本，复用未变化 chunks 与 embeddings；结构、哈希、冻结检索和测试全部通过后才原子切换 active pointer，并保留 previous 版本。

**证据**：54/942 基线封装时 942 个 embeddings 全部复用；候选激活和 rollback 在同一 Web 进程验证通过。索引发布门槛真实运行结构通过、检索 8/10、required failures 0。

**代价**：本地需要保留多个索引版本；CI 因不持有本地索引不能覆盖这一层。

## D9：安全策略必须早于检索和模型

**问题**：如果先检索、读记忆或调用模型再拒绝，敏感路径已经被触发；检索资料本身也可能包含指令型文本。

**决定**：查询入口先处理提示注入、凭据索取、跨用户记忆和明确知识库外实时请求；正常流程把证据与记忆标记为不可信数据，并将安全审计纳入 `quality_pass`。

**证据**：8/8 冻结安全案例通过；真实 Web 拒绝与知识边界请求均为 0 来源、0 记忆写入、无模型调用。

**代价**：规则有意追求高精度，不能替代开放域安全分类器；来源冲突依赖显式 metadata。

## D10：质量门槛只有一个入口

**问题**：本地、CI、安全回归和索引发布各自运行命令，长期容易漏跑或产生不同标准。

**决定**：统一入口执行依赖、编译、完整测试、安全门槛和 JavaScript；CI 调同一脚本，本地可通过 manifest 追加真实索引门槛。

**证据**：作品集阶段完整门槛 139/139 测试、8/8 安全案例和 JavaScript 均通过；追加候选 manifest 后索引门槛通过；GitHub Actions 主线任务通过。

**代价**：索引门槛仍只能在具备本地 Chroma 和 embedding 环境的机器上执行。
